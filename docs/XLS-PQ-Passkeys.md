## 1. Abstract

The alphanet `Passkey` amendment lets an account register WebAuthn passkeys and sign with them, but only with P-256 keys (COSE algorithm -7, ES256). `PasskeyMLDSA` adds ML-DSA-44 passkeys (COSE algorithm -48, RFC 9964): a passkey list may hold ML-DSA-44 public keys next to P-256 ones, and a `PasskeySignature` whose `SigningPubKey` is an ML-DSA-44 key is verified exactly like a P-256 one, the signature over `authenticatorData ‖ SHA-256(clientDataJSON)` being pure ML-DSA-44 with an empty context. No field, transaction, ledger entry or result code is added.

## 2. Motivation

A passkey has **full authority** over its account: `Transactor::checkSingleSign` accepts any key of the passkey list, whatever the master-key flag, as it accepts the `RegularKey`. In the alphanet a passkey is always P-256, and its public key is on the ledger from the moment it is registered (`PasskeyListSet` stores it in clear). A quantum computer that can run Shor's algorithm on P-256 can therefore derive the passkey's private key from the ledger alone, without the account ever signing, and sign anything for the account.

So on any account with a passkey, a P-256 passkey is a quantum backdoor with full authority, and none of the post-quantum measures available today closes it:

- moving the master key and the `RegularKey` to ML-DSA-44 (the `Quantum` amendment) and disabling the master key does not remove the passkey's authority;
- the passkey list can be neither replaced nor removed in this build (defect P6, `FIANSO-SPEC.md` §6.14), so a P-256 passkey cannot be rotated out.

`PasskeyMLDSA` lets an account keep the passkey user experience (a credential held by an authenticator, shown by a WebAuthn ceremony) with a key that no known quantum algorithm breaks, and lets an account be fully post-quantum: master key disabled, `RegularKey` the black hole, and an ML-DSA-44 passkey as its only authority (test `testFullyPostQuantum`).

## 5. Rules

### 5.1 `PasskeyListSet`

With the amendment, each `PublicKey` is a P-256 key (65 bytes, `0xF6 ‖ X ‖ Y`) or an ML-DSA-44 key (1 312 bytes, raw, no prefix); both kinds may share one list. Without it, an ML-DSA-44 key is refused as before with `temMALFORMED`. A value of any other size is no key and is refused in both cases. The other rules of `PasskeyListSet` are unchanged (no duplicate `PasskeyID`, no duplicate `PublicKey`, a non-empty list; one list per account, which cannot be replaced, defect P6).

### 5.2 Signature check (`STTx::checkSign`, stateless)

When the amendment is enabled and the `SigningPubKey` is an ML-DSA-44 key with a `PasskeySignature`, the node:

1. parses `ClientDataJSON` as a JSON object; `type` must be the string `"webauthn.get"`; `challenge` must be a string;
2. decodes `challenge` as base64url and compares it **byte for byte** with the transaction's signing data (`STX\0` followed by the fields that are signed, the same bytes a `TxnSignature` covers). This path is new, so it compares bytes whatever `fixPasskeyChallenge` says;
3. verifies `Signature` with the `SigningPubKey` over `AuthenticatorData ‖ SHA-256(ClientDataJSON)`: FIPS 204 ML-DSA-44 `Verify`, pure (no pre-hash), empty context. The signature must be exactly 2 420 bytes.

As for P-256, the node does not check the relying party, the origin, the flags or the signature counter in `AuthenticatorData`, nor any other member of `ClientDataJSON`.

### 5.3 Form

- A `TxnSignature` next to an ML-DSA-44 `PasskeySignature` is refused (the `fixP256StrictDer` rule, which the amendment requires): nothing would check it, and it would only change the transaction's ID.
- Without the amendment, a `PasskeySignature` next to an ML-DSA-44 key is refused with `fixP256StrictDer` and ignored without it (then only a `TxnSignature` can carry the transaction), as before.
- P-256 passkeys are unchanged.

### 5.4 Authorization (`Transactor::checkSign`, against the ledger)

An ML-DSA-44 passkey signature authorizes **only** through the passkey list of the account (of the `Delegate` for a delegated transaction): an entry must hold the `SigningPubKey` (same bytes) **and** the same `PasskeyID` as the `PasskeySignature`. Otherwise `tefBAD_AUTH`, even when the key is the account's master key, its `RegularKey` or a session key: those keys sign with a `TxnSignature`. Since `PasskeySignature` is not signed, binding `PasskeyID` to the list entry gives it exactly one accepted value, so a relay cannot re-hash the transaction by changing it (the alphanet P-256 path still allows it, a known issue of `Passkey`).

A list key also keeps the alphanet's raw form: the ML-DSA-44 key of a list entry may sign with a `TxnSignature`, like a P-256 passkey (full authority).

Signing sessions: an ML-DSA-44 passkey opens, closes and is refused as a session key exactly as a P-256 one (`SigningSessionSet` refuses a session key that is a passkey with `tecNO_PERMISSION`). A session-signed transaction may not carry an ML-DSA-44 `PasskeySignature` (`tefBAD_AUTH`); the session key signs with a `TxnSignature`. So a key that is already a session key of the account when it is added to the passkey list (the opening refuses a passkey, not a later registration) cannot sign through WebAuthn while that session lives: its transactions take the session path. Once the session is deleted or has been cleaned up, it signs as a passkey (test `testSessionKeyAddedToList`).

The binding covers every path that authorizes a top-level signature: a `Delegate` signs with its own ML-DSA-44 passkey against its own list, an outer `Batch` is signed by the account's passkey, and a sponsored transaction carries the account's passkey signature at the top level next to the sponsor's `SponsorSignature` (test `testOtherSigningPaths`). No inner object format allows a `PasskeySignature` (`Signer`, `BatchSigner`, `SponsorSignature`, `CounterpartySignature`, `WitnessSignature`).

### 5.5 Activation

Until the amendment and the three it needs are enabled, `checkValidity` keeps no signature verdict on a transaction that holds a `PasskeySignature` next to an ML-DSA-44 key, and `NetworkOPs` and `PeerImp` do not mark it `BAD` (`isSignatureVerdictCacheable`). With `fixP256StrictDer` already enabled, the amendment turns such a verdict from refused to verified; if `fixP256StrictDer` comes last, the PasskeySignature goes from ignored to verified, so a verdict changes in both directions, and the `fixP256StrictDer` rule of the same function (no verdict on any transaction with a `PasskeySignature` before it) covers that order. No verdict crosses either activation. A verdict forced by `forceValidity` still holds.

`fixP256StrictDer` is required for that reason: before it no verdict on a transaction carrying a `PasskeySignature` is ever cached, so every ML-DSA-44 passkey transaction would be verified again on every `checkValidity` call (about 2.4 KB of signature and 1.4 KB of challenge each time) for as long as the fix stayed off. Cost before activation: one verification per `checkValidity` call for such a transaction.

## 6. Client mapping (wire format)

**Registration.** From `navigator.credentials.create` with `pubKeyCredParams: [{type: "public-key", alg: -48}]`, read the credential public key (a COSE key with `kty` 7 (AKP), `alg` -48, `pub` (label -1)). Submit:

```json
{
  "TransactionType": "PasskeyListSet",
  "Account": "r…",
  "Passkeys": [
    {
      "Passkey": {
        "PasskeyID": "<hex of the credential id>",
        "PublicKey": "<hex of pub, 1 312 bytes>"
      }
    }
  ]
}
```

The `PasskeyID` is whatever the account registers (the credential id, as bytes); it must be repeated, identical, in every `PasskeySignature` of that key.

**Signing.**

1. Fill the transaction, with `SigningPubKey` = the 1 312-byte key (hex) and no `TxnSignature`, `Signers` or `PasskeySignature`.
2. `signingData` = `encodeForSigning(tx)`: `0x53545800` (`STX\0`) followed by the canonical binary of the signing fields. It contains the 1 312-byte key, so it is about 1.4 KB.
3. Call `navigator.credentials.get` with `challenge` = `signingData` (the raw bytes) and `allowCredentials` = that credential. The browser puts `base64url(signingData)` (no padding) in `clientDataJSON.challenge`.
4. The authenticator returns `authenticatorData`, `clientDataJSON` and `signature` = ML-DSA-44 over `authenticatorData ‖ SHA-256(clientDataJSON)`, pure, empty context: 2 420 raw bytes (no DER, no COSE wrapping).
5. Add `"PasskeySignature": {"PasskeyID": <the registered id>, "AuthenticatorData": hex(authenticatorData), "ClientDataJSON": hex(the exact bytes returned), "Signature": hex(signature)}`, serialize and submit. `PasskeySignature` is not a signing field, so adding it does not change `signingData`.

Whether any shipping authenticator or browser creates `alg: -48` credentials is **UNVERIFIED**; the tests use a software authenticator. A software authenticator built on `@noble/post-quantum` (`ml_dsa44.sign(message, secretKey)` with no context) produces the same signature format the node verifies, but no node has yet been shown to accept one (the node accepted Stax ML-DSA-44 signatures over transactions on the public AlphaNet, `docs/DEVLOG.md`).

## 7. Tests (suite `PasskeyMLDSA`, SIMULATED authenticator)

Refused before the amendment (and without `Quantum`, `Passkey` or `fixP256StrictDer`): an ML-DSA-44 list, and an ML-DSA-44 `PasskeySignature`, answered "Invalid signature." on every submission. With it: registration (alone and next to a P-256 key); a payment by WebAuthn (`tesSUCCESS`, a 2 420-byte signature, no `TxnSignature`); refusals for a challenge over other bytes, `webauthn.create`, no challenge, an altered signature, altered `AuthenticatorData`, a truncated or extended signature, a DER signature, a `TxnSignature` next to it (even a valid one); a key not in the list, another account's list, another `PasskeyID`, an ML-DSA-44 master key or `RegularKey` signing through WebAuthn (`tefBAD_AUTH`); the byte comparison without `fixPasskeyChallenge`; a fixed vector made outside rippled (@noble/post-quantum 0.7.1 and ripple-binary-codec 2.11.0, generator `packages/core/spikes/passkey-mldsa-vector.ts`) verified as it is and refused with one bit changed; the binding on the delegate, outer `Batch` and sponsor paths; a fully post-quantum account (black-hole `RegularKey`, master disabled, only an ML-DSA-44 passkey); the passkey opening and closing a session, refused as a session key, a session key refused through WebAuthn, and a session key added to the list later signing through WebAuthn only after its session; P-256 passkeys unchanged, both kinds in one list; the same blob refused before and accepted after the activation; the verdict cache in both directions, a forced verdict, and `NetworkOPs` not marking it `BAD`.

## 8. Not covered

- **Rotation and revocation (P6).** One passkey list per account, never replaced nor removed. An ML-DSA-44 passkey is not exposed to a quantum computer, but a lost or stolen authenticator keeps full authority. A fix of `SetPasskeyList::doApply` is a separate `Passkey` defect.
- **`PasskeyListSet` is `Delegable`** (review of Transia-RnD/rippled#29): a delegate holding that permission can register its own passkey, ML-DSA-44 included, and take the account over. **The reserve** is not checked when the list is created (same review). Both are `Passkey` defects, not fixed here.
- **The list's size** is bounded only by the transaction size. An account's single-signed transactions that are not signed by its master key or `RegularKey` hash every list key to find a match (`checkSingleSign`); 1 312-byte keys make that up to 20 times more bytes per entry than P-256 ones. This draft documents the cost rather than capping the number of ML-DSA-44 entries; a cap, which the single owner-count unit of the list would justify, is a decision for the `Passkey` amendment's list rules.
- **The P-256 `PasskeyID`** stays unbound (alphanet behaviour, "Known issues" of `rippled/API-CHANGELOG.md`).
- **`asfDisableMaster`** does not count a passkey list as an alternative key (asked on XLS-83d); a fully passkey-controlled account needs a black-hole `RegularKey` first.
- **Higher parameter sets** (ML-DSA-65, COSE -49; ML-DSA-87, COSE -50), as XLS-0103 also leaves them to a later XLS.
