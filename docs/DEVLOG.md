## 2026-10-24: independent review of the web app, and what it changed

## 2026-10-25: `SessionMaxTxCount`, a bound on how many transactions a session signs

- **What:** `SigningSessionSet` takes an optional `SessionMaxTxCount` (UINT32 115), from 1 to `kMaxSessionTxCount` = 100 000 (`temMALFORMED` otherwise), in every mode. - **Why:** the device profiles (agent, game, trading, streaming, minting) bound the number of actions as well as the amounts; modes A and P had no bound but the duration.

## 2026-10-25: rotating the RegularKey on every payment, in a Batch

- **What:** an account whose master key is disabled pays only through an all-or-nothing Batch signed by its current RegularKey K_n, carrying [Payment, SetRegularKey -> K_{n+1}]. Inner transactions carry no signature, so a payment reveals only K_n, the key it retires; the ledger stores K_{n+1} as an AccountID (a hash), so the public key in force is never on the ledger. `SetRegularKey` has no master-key check (unlike `asfDisableMaster`), so it works as an inner transaction.
- **rippled:** `KeyRotationBatch` (`rippled/src/test/app/KeyRotationBatch_test.cpp`): three rotations, each paying bob and installing the next key (the outer's `SigningPubKey` is K_n and its blob does not hold K_{n+1}'s public key), the retired key `tefBAD_AUTH` and the master `tefMASTER_DISABLED` after each; a Batch whose payment fails (`tecNO_DST_INSUF_XRP`) leaves the RegularKey unchanged (only the outer fee and sequence consumed); a rotation to a key never revealed stores its AccountID only (the account root holds no copy of its public key). 3 cases, 154 tests, 0 failures; `Batch` and `SigningSessionsBatch` still pass.
- **Live:** `pnpm --filter @carbs/passkey-wallet rotation-demo` (`GENESIS_SEED`, `XRPLD_WS`, default `ws://127.0.0.1:16006`). Keys come from one 32-byte secret (`ROTATION_SECRET`, random by default): key n is the secp256k1 family seed whose entropy is the first 16 bytes of SHA-512("carbs-rotation" | secret | n), index 0 being the master; chosen over BIP32 (not a dependency) and over `deriveKeypair`'s `accountIndex` because each key stays a plain family seed the existing `signWithSeed` signs with. On the Mac standalone node: 5 payments, every inner `tesSUCCESS`, K1–K5 then refused (`tefBAD_AUTH`), the master too (`tefMASTER_DISABLED`); `account_tx` shows each of K1–K5 exactly once, in the Batch installing the next key, and K6 (in force) never.
- **Limit:** the master public key is revealed by the two setup transactions (SetRegularKey, then `asfDisableMaster`, which needs the master's own signature and cannot be an inner transaction); it is disabled afterwards.
